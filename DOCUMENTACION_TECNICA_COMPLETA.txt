================================================================================
SECCION 1. IDENTIFICACION Y DESCRIPCION DEL PROYECTO
================================================================================

Caon es una aplicacion web para explorar estilos de juego de equipos-entrenador
de Liga MX y simular partidos jugada a jugada. Usa agregados derivados de
eventos Hudl StatsBomb, no eventos crudos en la aplicacion publicada.

Funcionalidades verificadas:
1. Plan de juego: percentiles de catorce metricas y etiquetas tipo FC.
2. Mapa de estilos: coordenadas con y sin balon, temporadas, trayectorias y
   equipos parecidos.
3. Simulacion completa: dos equipos, posesiones, pases, conducciones, tiros,
   goles, faltas, tarjetas, corners, tiros libres, penales y expulsiones.
4. Laboratorio tactico: la interfaz permite describir/reproducir jugadas; la
   implementacion visual esta principalmente en frontend/index.html.
5. Simulacion rapida: agregacion de multiples simulaciones mediante
   engine.simulateMany.

Actores observados: usuario del navegador, servidor FastAPI, pipeline de
construccion y servicios StatsBomb. No se encontro autenticacion de usuario ni
roles de aplicacion.

Entradas principales: solicitudes HTTP, seleccion de entidades en la interfaz,
modelo JSON local y, para reconstruccion, respuestas de StatsBomb y archivos
Open Data. Salidas: HTML/JS, respuestas JSON, logs de pipeline, model.json,
reportes de validacion y referee.

================================================================================
SECCION 3. ARQUITECTURA Y RELACIONES
================================================================================

La arquitectura real es un pipeline offline mas un servidor de lectura:

StatsBomb API / Open Data
  -> data/cache o data/opendata
  -> pipeline/extract.py
  -> data/extract/<fuente>_<match>.json
  -> pipeline/build_model.py
  -> model/model.json
  -> app/main.py y frontend/index.html
  -> frontend/engine.js
  -> visualizacion y resultados de simulacion

Capas observadas:
- Adquisicion: statsbomb.py, download.py, download_lineups.py y
  download_opendata.py.
- Procesamiento: extract.py resume eventos; build_model.py agrega y calibra.
- Servicio: app/main.py carga el JSON bajo demanda y lo expone.
- Presentacion/simulacion: index.html y engine.js.
- Verificacion: validate.js, targets.py y referee.js.

No hay llamadas del backend a engine.js: la simulacion ocurre en navegador o
Node. El backend sirve archivos estaticos y el JSON.

   - Descarga para Barcelona 2009-11, La Liga competicion 11, temporadas 21 y

================================================================================
SECCION 8. PROCESOS INTERNOS Y LOGICA DE NEGOCIO
================================================================================

PROCESO P1 - Construccion de entidades.
1. all_matches recorre SEASONS_ALL y descarta partidos no disponibles.
2. SPECIAL se agrega primero.
3. build_entities detecta el entrenador mas reciente por equipo de temporada
   351 y retrocede hasta el cambio de entrenador.
4. Cada partido se asigna si equipo, substring de entrenador y fechas coinciden.
5. Resultado: lista de entidades con matches {mid, side, date}.
Referencia: [REF: pipeline/entities.py :: build_entities :: lineas 29-59].

PROCESO P2 - Extraccion de un partido.
1. process carga eventos MX desde cache u Open Data desde data/opendata.
2. Conserva periodos <=4, agrupa eventos por possession y crea acumuladores por
   equipo.
3. Identifica acciones, penales, reinicios administrativos, recuperaciones y
   balon parado.
4. Clasifica cada accion por zona/fase y registra desenlace: movimiento, tiro,
   perdida, falta, corner o penal.
5. Acumula disciplina, xG, lanzadores, posiciones, actores y metricas.
6. Escribe un JSON compacto en data/extract.
Referencia: [REF: pipeline/extract.py :: process :: lineas 152-351].

PROCESO P3 - Construccion del modelo.
1. Acc.add suma CHAIN_KEYS y SCALAR_KEYS.
2. build_model produce att del equipo y dfn a partir del rival.
3. build_shape elige formacion, puestos y jugadores representativos.
4. Se calculan metricas, percentiles, etiquetas, coordenadas de mapa y roles.
5. Se agregan league y entidades real/opendata/synthetic.
6. Se escribe model/model.json.
Referencia: [REF: pipeline/build_model.py :: Acc, build_shape y main ::
lineas 39-115 y 311-497].

PROCESO P4 - Servicio.
load_model verifica existencia, lee JSON y cachea por mtime. Si no existe
devuelve HTTP 503. team busca id exacto y devuelve HTTP 404 si no existe.
Referencia: [REF: app/main.py :: load_model y team :: lineas 25-67].

PROCESO P5 - Simulacion.
1. matchup calcula rates de ataque A y defensa D, combinados con la liga.
2. Cada accion muestrea desenlace en la zona y fase actual.
3. move cambia zona; lossO inicia posesion rival y transicion; reinicios crean
   corner, tiro libre, saque, saque de meta o penal.
4. tiros generan xG y resultado aleatorio; goles y tiempo muerto actualizan
   estado.
5. tarjetas/rojas modifican probabilidades mediante ajustes logit.
6. simulate devuelve score, posesion, tilt, stats, log y params.
7. simulateMany repite N semillas deterministas derivadas de seed y promedia.
Referencia: [REF: frontend/engine.js :: rates, matchup, simulate y
simulateMany :: lineas aproximadas 40-180, 600-900].

PROCESO P6 - Coreografia.
choreograph transforma eventos de simulacion en posiciones de 22 jugadores y
balon, aplicando reinicios, fuera de juego, distancias reglamentarias, areas,
circulo central y expulsados. Su contrato exacto se encuentra en
frontend/engine.js y es consumido por la animacion de index.html.

================================================================================
SECCION 11. ALGORITMOS, MODELOS Y CALCULOS
================================================================================

El algoritmo central es una cadena de Markov discreta por zona y fase. Para cada
desenlace se combina ataque, defensa y liga:
  logit(p) = logit(p_ataque) + logit(p_defensa) - logit(p_liga)
La salida se acota y se renormaliza cuando la suma excede 0.97. xG se combina
multiplicativamente y se acota a [0.005, 0.9].

La zona es una cuadricula 6x3. La fase T dura 10 segundos desde recuperacion
en juego abierto; la fase E es el resto. Se usan pesos de tiempo muerto por
tipo de reanudacion y una unidad calibrada contra frecuencia de eventos.

El motor usa mulberry32 para aleatoriedad reproducible. simulateMany agrega
goles, xG, tiros, posesion, recuperaciones, faltas, tarjetas, corners,
fuera de juego y distribucion de marcadores.

Metricas de estilo incluyen posesion, verticalidad, ritmo hacia porteria,
altura defensiva, volumen de presion, PPDA, contrapresion, saque largo,
centros, contragolpe, tiros tras robo alto, xG, solidez y xG de balon parado.
Los valores visibles son percentiles, no predicciones.

No se encontro un modelo de aprendizaje entrenado para inferencia durante el
servido. scikit-learn aparece solo como dependencia de research/clusters.py.

- El pipeline depende de datos/credenciales externos y de versiones compatibles.

================================================================================
SECCION 14. ERRORES, RESTRICCIONES Y CASOS LIMITE
================================================================================

- Sin model.json: HTTP 503 con instruccion de ejecutar build.
- Entidad inexistente: HTTP 404.
- Sin credenciales: termina con mensaje de configuracion.
- Respuesta API vacia: ValueError.
- Cache no UTF-8: intenta cp1252.
- Cache JSON corrupto: elimina y descarga de nuevo.
- Extracto corrupto o ausente al cargar: build_model retorna teams vacio; esto
  permite continuar pero puede omitir datos silenciosamente.
- Eventos sin primera accion o sin location se saltan en varias ramas.
- Posesiones administrativas se saltan al buscar el siguiente estado.
- Periodos mayores que 4 se excluyen.
- Penales se excluyen de la cadena normal y se modelan aparte.
- Muestras pequenas se acercan a liga con K=8, limitacion estadistica inherente.
- simulateMany limita claves de marcador a 5 mediante min(a,5)/min(b,5).
- No se encontro mecanismo de persistencia transaccional ni concurrencia de
  escritura; el servicio esta disenado para lectura.

================================================================================
SECCION 17. GLOSARIO TECNICO
================================================================================

Entidad: combinacion de equipo, entrenador y ventana temporal.
Att: agregado de acciones del propio equipo con balon.
Dfn: agregado de acciones del rival cuando ataca a la entidad.
E: ataque establecido.
T: transicion durante los primeros 10 segundos tras recuperacion.
SP/BP: balon parado peligroso.
LTO: matriz que indica donde comienza la siguiente posesion.
XG: expected goals provisto por StatsBomb.
PPDA: acciones defensivas por pase rival.
Shape: once tipo y posiciones medias con/sin balon.
Actors: distribucion de acciones por puesto y zona.
K: numero de pseudo-partidos de regularizacion hacia la liga.
League: acumulado de referencia usado para tasas y percentiles.
Coreografia: conversion de eventos abstractos a jugadores, balon y posiciones.

SECCION 19. GUIA DE LECTURA PARA OTRA INTELIGENCIA ARTIFICIAL
================================================================================

Orden recomendado:
1. Leer README.md para objetivo, comandos y limites de distribucion.
2. Leer app/main.py para contrato HTTP y carga del modelo.
3. Leer model/model.json para estructura concreta y entidades disponibles.
4. Leer extract.py para semantica de zonas, fases y desenlaces.
5. Leer build_model.py para agregacion, estilos, formas y mapas.
6. Leer engine.js para la simulacion y coreografia.
7. Leer validate.js/referee.js para verificaciones y restricciones.
8. Leer docs/DOCUMENTACION.md para contexto metodologico y decisiones.

Puntos de entrada: uvicorn app.main:app, pipeline/run.py y require de
frontend/engine.js en Node. Fuentes: StatsBomb API, Open Data y model.json.
Transformaciones esenciales: zone, clasificacion T/E, agregacion att/dfn,
regularizacion K y combinacion logit.

Convenciones:
- Las coordenadas y zonas siempre deben interpretarse en orientacion del equipo
  que ataca; mirrorZ adapta la orientacion rival.
- JSON con null significa dato ausente; una clave no presente significa que el
  productor no la incluyo.
- VERIFIED/INFERRED/UNVERIFIED/NOT_FOUND/NOT_ACCESSIBLE indican certeza y no
  deben confundirse.
- Una cifra historica de docs no equivale a una prueba ejecutada ahora.

La documentacion permite responder "donde" mediante las referencias REF y
permite reconstruir "que ocurre despues" siguiendo los flujos P1-P6. Antes de
afirmar que el sistema funciona con datos nuevos, una IA debe distinguir la
implementacion comprobada del modelo preconstruido y ejecutar download,
extract, build, validate y referee en un entorno con credenciales y Node.
